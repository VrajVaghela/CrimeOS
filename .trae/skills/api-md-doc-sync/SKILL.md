# API.md Documentation Sync

## Description
Documentation drift between `ARCHITECTURE.md` (the source-of-truth contract) and `backend/API.md` (the running log of what's actually implemented) is one of the easiest ways for this project to become confusing across 16 checkpoints. This skill makes updating both a fixed, repeatable step rather than something left to memory.

## When to Use
- Immediately after any checkpoint that adds, changes, or removes an HTTP endpoint — this is the last step of nearly every backend checkpoint in Stages 1-3.
- When a checkpoint's endpoint wasn't pre-specified in `ARCHITECTURE.md` §1.5 (e.g. Stage 2 Checkpoint 4's summary/timeline endpoints) — in that case, update `ARCHITECTURE.md` §1.5 FIRST via `str_replace`, then mirror into `API.md`.

## Instructions
1. **Format** (must match exactly — this is what the audit-wrapped-handler skill and frontend api-wrapper skill both key off of):
   ```
   ### <Human-readable grouping, e.g. "Legal Request Engine">
   ```
   <METHOD> <path>
   Body:    { "field": "type/example", ... }   // omit if no body
   Resp <status>:{ "field": "...", ... }
   Errors:  <status> <condition>, <status> <condition>   // omit if none beyond the standard envelope
   ```
   ```
2. **Order**: endpoints appear in `API.md` grouped by domain in the same order as `ARCHITECTURE.md` §1.5 (Entity Extraction → Legal Request Engine → Dispatch Simulation → Response Analytics → Audit). New endpoints within an existing group go at the end of that group's block, not alphabetically.
3. **Cross-check before writing**: if the endpoint already has a contract defined in `ARCHITECTURE.md` §1.5, copy it verbatim — do not paraphrase or "improve" the wording, since the frontend TypeScript types are generated by hand against this exact text.
4. **New endpoint not yet in ARCHITECTURE.md**: use `str_replace` to insert it into the correct §1.5 subsection of `ARCHITECTURE.md`, matching the existing format precisely, THEN copy into `API.md`. Never let `API.md` contain an endpoint that `ARCHITECTURE.md` doesn't also describe.
5. **Error cases**: always list every non-2xx status the handler can actually return (checked against the handler code, not guessed) — `400` validation, `404` not found, `409` conflict, `422` semantic validation, etc.
6. **Never delete an endpoint entry** even if deprecated mid-project — mark it `[DEPRECATED — superseded by <endpoint>]` instead, so the history stays legible.

## Example
```
### Legal Request Engine

GET /api/v1/cases/{caseId}/legal-requests/summary
Resp 200:{ "by_status": {"DRAFTED": 2, "SENT": 5}, "total": 11 }

GET /api/v1/cases/{caseId}/legal-requests/timeline
Resp 200:{ "requests": [ { "legal_request": {...}, "events": [...] } ] }
```
